#### A.2.1 Host-side migration runbook (lead-executed; ordering integrates with main-ADR §5)

**Critical ordering constraint:** the django (+ celery_worker) container reads `_loader.py` and `_prefs.py` at runtime and may hold file descriptors open against `/app/.scitex/cloud/*`. The migration must happen **with the affected containers stopped** to avoid the `mv` racing against open handles. Slot this between main-ADR §5.4(b) `sed .env.prod` and §5.4(c) volume clone — at T-0, after `docker compose down` completes.

```bash
# Step §5.4(b.5) — User-data path migration (Q2)

# === Layer 1: operator's host filesystem ===
# Pre-condition: django + celery_worker stack is DOWN (§5.4(a) already ran).
# Also stop proj-scitex-hub agent first if it has ~/.scitex/ bound:
#   sac agents stop proj-scitex-hub   # (lead runs this on NAS)

# 1a. Verify nothing has the dir open
lsof +D /home/ywatanabe/.scitex/cloud 2>/dev/null | head
# Should be empty. If not, identify the holder and stop it.

# 1b. Backup
BAK_USERDATA="$BAK/userdata-host"   # $BAK was set in main-ADR §5.1
mkdir -p "$BAK_USERDATA"
tar -C /home/ywatanabe/.scitex -czf "$BAK_USERDATA/cloud.tar.gz" cloud
ls -lh "$BAK_USERDATA/cloud.tar.gz"   # sanity: non-trivial size

# 1c. Move (atomic on same filesystem)
mv /home/ywatanabe/.scitex/cloud /home/ywatanabe/.scitex/hub

# 1d. Compat symlink — external tools that still type the old path keep working
ln -s hub /home/ywatanabe/.scitex/cloud
# Verify
ls -l /home/ywatanabe/.scitex/cloud    # → symlink -> hub
ls /home/ywatanabe/.scitex/cloud/      # lists same contents as ~/.scitex/hub/

# === Layer 2: docker named volume scitex_config_volume ===
# Migrate the cloud/ subdir to hub/ inside the named volume.
docker run --rm -v scitex_config_volume:/data alpine sh -c '
  set -e
  cd /data
  if [ -d cloud ] && [ ! -e hub ]; then
    cp -a cloud hub.tmp && mv hub.tmp hub
    rm -rf cloud
    ln -s hub cloud
    echo "migrated /data/cloud -> /data/hub + symlink"
  elif [ -L cloud ] && [ -d hub ]; then
    echo "already migrated"
  else
    echo "unexpected state — manual check needed"; exit 1
  fi
'
# Idempotent: re-runs are no-ops once migrated.

# === Verify before proceeding to §5.4(c) clone ===
ls -la /home/ywatanabe/.scitex/                                    # cloud → hub symlink
docker run --rm -v scitex_config_volume:/data alpine ls -la /data  # same shape inside volume
```

After the migration runs, §5.4(c) volume clone proceeds normally. Verify at session time whether `scitex_config_volume` should be added to the §5.4(c) clone loop (currently lists `postgres_data / redis_data / gitea_data / static_volume / media_volume`) — if so, the volume-internal migration above is carried into the new `scitex-hub-prod_scitex_config_volume` automatically because clone happens AFTER the migration.

#### A.2.2 Rollback for Q2 (folds into main-ADR §6)

If smoke (§5.5) fails AND rollback (§6) is triggered:

```bash
# Layer 1 rollback
rm /home/ywatanabe/.scitex/cloud                                 # the symlink
mv /home/ywatanabe/.scitex/hub /home/ywatanabe/.scitex/cloud     # undo the move
# (backup tarball at $BAK/userdata-host/cloud.tar.gz is the second safety net)

# Layer 2 rollback (named volume)
docker run --rm -v scitex_config_volume:/data alpine sh -c '
  set -e
  cd /data
  if [ -L cloud ] && [ -d hub ]; then
    rm cloud && mv hub cloud
    echo "rolled back /data/hub -> /data/cloud"
  fi
'
```

#### A.2.3 Deprecation window for the symlink

Drafter recommends keeping the symlink ≥30 days (same window as the old volumes per main-ADR §7). During that time, lead/operator sweep external tooling for hardcoded `~/.scitex/cloud/` references and migrate them one at a time. After 30 days of green prod + zero hits on the symlink (verify via `stat -c '%X' ~/.scitex/cloud` access-time check), it can be removed.


# Hub CI cycle-time audit

Measured 2026-09-15 from the latest 100 Actions runs and each recent job payload.

## Findings

- The successful pytest run `35007084686` was the PR critical path: Python 3.11/3.12/3.13 took 6.62/9.85/8.30 minutes on `scitex-04-docker-03`, `scitex-03-docker-02`, and `scitex-03-docker-01`. In run `35012516899`, setup/install was only 38–43 seconds while pytest took 272–487 seconds, so dependency caching is effective and test execution is the bottleneck.
- The fleet query measured six online `scitex-docker` slots on compute-03/04 and seven online `scitex-local-cpu` slots across compute-01/03/04. **No `scitex-docker` runner is registered on compute-02**, so this change does not claim or route Docker shards there. The six Docker runners expose only the shared `scitex-docker` label, not host-specific labels, so GitHub cannot enforce one shard per physical node. Three Spartan runners were online under `spartan-cpu`, but no Hub workflow targets that label. The change keeps only measured repo labels instead of inventing host labels; fork PRs retain the explicit hosted fallback and pre-checkout self-hosted refusal.
- Recent non-Python legs were already parallel: CodeQL 1.35–1.67 minutes, quality 1.65–1.80, TypeScript 2.23–2.73, Vitest 0.87–1.48, terminal 0.88–0.97, security regression 3.38–3.78, and E2E 8.82–9.18 on hosted runners.
- Every non-mutating workflow already has per-workflow/per-ref concurrency with PR-only stale-run cancellation. Recent superseded PR generation `35012506766`–`35012507519` confirms cancellation works across pytest, E2E, CodeQL, docs, quality, imports, screenshots, guards, and language/security—not only E2E. Release, pack publication, CLA mutation, and auto-merge are intentionally non-cancellable.
- Duplicate full installs remain across isolated E2E/screenshots/TypeScript/security jobs. Sharing complete virtualenv artifacts is unsafe across Python versions, runner images, and absolute worktree paths. `setup-uv` download caches are keyed from `pyproject.toml`; npm jobs still use `npm install` rather than a lockfile-enforced shared cache and are follow-up candidates. The measured pytest install is only 14–17 seconds, so artifact transfer would increase its critical path.
- The previous `--cpus 8` container limit and fixed eight xdist workers left roughly three quarters of each compute-03/04 host idle during the wall-clock bottleneck. The cap is removed. Worker selection now takes the minimum of hardware CPU count, process affinity, and cgroup-v2 quota (32 in the local verification environment), while `nice -n 10 ionice -c 2 -n 7` makes the all-core batch subordinate to interactive CPU and I/O work.

## Change and estimate

The supported-version policy is event-aware: an ordinary pull request targeting `develop` runs Python 3.11 only, while pull requests targeting `main` or a release branch, pushes, nightly schedules, and manual runs select 3.11/3.12/3.13. Every selected version is split into three deterministic, disjoint file groups. Files stay indivisible (preserving xdist grouping semantics) and are greedily balanced by test-definition count. A stable `Python CI aggregate gate` rejects a failed, cancelled, or skipped selector/shard.

Using the observed successful critical path (9.85 minutes), observed fixed overhead (~0.7 minutes), three file shards, six measured Docker slots, and the authorized 8→32-worker increase, the ideal ordinary-PR estimate is `0.7 + (9.85 - 0.7) / 3 / 4 = 1.5 minutes`; allowing 40% parallel overhead gives ~2.1 minutes (79% lower). A full 3-version release/nightly uses two waves: ideal 2.9 minutes, conservative ~4.1 minutes (58% lower). These are estimates, not benchmarks: database contention, the shared host label, and non-CPU-bound tests determine realized results. No test file, database engine, language, or security leg was removed.

The same generic policy is proposed centrally in `scitex-ai/.github` PR #48 (commit `16d75e45f10ebd24a1ea53fc3380d9dd3c719124`). Hub cannot yet become a safe thin caller: the central job cannot express Hub's required non-root `buildpack-deps:noble` job container plus the two read-only Docker CLI mounts. Running directly on persistent `scitex-docker` hosts would expose the shared runner `$HOME`; dropping the mounts would lose compose-config tests. GitHub does not document empty/conditional `jobs.<job>.container` the way it documents conditional service images, so an unverified optional-container input was not shipped. The local caller-specific workflow remains until that upstream contract is implemented without changing the other 25 callers' execution environment.

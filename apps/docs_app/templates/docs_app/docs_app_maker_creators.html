Architecture

Every workspace module consists of these layers:

Layer File Purpose
1. Registry workspace_app/registry.py ModuleConfig entry — single source of truth
2. Views your_app/views.py Full page view + context builder function
3. Templates your_app/templates/ index.html (full page) + index_partial.html (AJAX)
4. URLs config/urls.py path("your/", include(("apps.your_app.urls", "your_app")))
5. Skill your_app/skill.py LLM integration — capabilities, tool prefixes
6. Tests your_app/tests.py ModuleTestMixin validates all layers automatically
The Example App at /example/ is the authoritative reference implementation. Copy its structure for new modules.

CLI Workflow (Recommended)

The fastest way to create and deploy a full app is via the scitex-cloud CLI. This gives you a complete project with manifest, Platform Services integration, and Gitea sync.

Step 1. Scaffold 

# Create a new app with all boilerplate
scitex-cloud app init /path/to/my_app --name my_research_app \
    --label "My Research Tool" --icon "fas fa-flask"

# Or with React frontend:
scitex-cloud app init . --name my_app --frontend react

Step 2. Develop locally 

# Initialize git
cd /path/to/my_app
git init && git add . && git commit -m "Initial scaffold"

# Edit manifest.yaml, views, templates, jobs...

Step 3. Upload to workspace 

# Creates project on server + Gitea repo + pushes code
scitex-cloud workspace upload --name my-research-app \
    --description "My research tool"

# Other workspace commands:
scitex-cloud workspace list          # List your projects
scitex-cloud workspace sync          # Pull + push changes
scitex-cloud workspace logout        # Clear cached token

Step 4. Validate and submit 

# Check app structure and security
scitex-cloud app validate .

# Submit for public listing (opens PR on scitex/apps registry)
scitex-cloud app submit . --token $SCITEX_CLOUD_TOKEN
The workspace upload command authenticates via JWT, creates a Django project (which auto-creates a Gitea repository), adds the git remote, and pushes your code.

Platform Services

Apps can use 7 built-in Platform Services via REST APIs instead of writing custom Django models, views, or Celery tasks. This lets you build powerful apps with just a manifest.yaml and frontend code.

Service API Prefix Purpose
DataStore /platform/api/data/ JSON-based CRUD with indexed virtual columns
FileVault /platform/api/files/ File upload/download scoped to app + project
JobQueue /platform/api/jobs/ Background task execution via Celery
ScitexBridge /platform/api/scitex/ Proxy to scitex Python package (io, stats, plt)
ExternalAPI /platform/api/external/ Proxied HTTP calls to whitelisted external services
RealtimeHub ws:// WebSocket channels for live updates
FrontendKit — Shared TS components (DataTable, Monaco, Viewer, Context Zoom)

Manifest

A manifest.yaml declares your app's data schemas, jobs, and service dependencies. Platform Services read this file to auto-configure everything. 

name: my-research-tool
label: My Research Tool
version: 0.1.0
icon: fas fa-flask
category: data
description: A tool for managing research samples.

datastore:
  Sample:
    fields:
      name: {type: string, max_length: 200, indexed: true}
      condition: {type: string, max_length: 100, indexed: true}
      measurement: {type: float}
      notes: {type: text}
      recorded_at: {type: datetime}
      tags: {type: json}
    permissions: owner_and_collaborators

jobs:
  export_samples:
    handler: my_research_app.jobs.export_samples.execute

scitex_modules: [io, stats]

The DataStore creates virtual indexed columns automatically — no Django migrations needed. Your frontend calls /platform/api/data/my-research-tool/Sample/ for CRUD operations.

No Django models required. The Platform Services DataStore provides JSON-based persistence with indexed lookups, so apps can store structured data without writing migrations.

ModuleConfig

Every module is defined by a ModuleConfig dataclass in workspace_app/registry.py:

Field Type Description
name str URL slug (e.g., "writer")
label str Display name (e.g., "Writer")
app_name str Django app name (e.g., "writer_app")
icon_fa str FontAwesome class (e.g., "fas fa-pen")
partial_template str AJAX partial template path
context_builder str Dotted path to context function
keyboard_shortcut str Alt+key shortcut (single letter)
order int Tab bar position (lower = leftmost)
status str "stable", "wip", "beta", "deprecated"
default_enabled bool Show in tab bar for new users
ai_hint str Short description for LLM context
accent_color str CSS variable name for module accent

Create a Module

Minimum file structure:

apps/mymodule_app/
├── __init__.py
├── apps.py                      # Django AppConfig
├── views.py                     # index_view + build_mymodule_context
├── urls.py                      # path("", views.index_view, name="index")
├── skill.py                     # LLM skill registration
├── tests.py                     # ModuleTestMixin validation
├── templates/mymodule_app/
│   ├── index.html              # extends "global_base.html"
│   └── index_partial.html      # standalone AJAX partial
└── static/mymodule_app/
    └── css/mymodule.css

Step 1. Add ModuleConfig to workspace_app/registry.py: 

ModuleConfig(
    name="mymodule",
    label="My Module",
    app_name="mymodule_app",
    icon_fa="fas fa-widget",
    partial_template="mymodule_app/index_partial.html",
    context_builder="apps.mymodule_app.views.build_mymodule_context",
    keyboard_shortcut="Y",
    order=75,
    ai_hint="Short description for LLM context",
    accent_color="mymodule",
)

Step 2. Add URL pattern to config/urls.py: 

path("mymodule/", include(("apps.mymodule_app.urls", "mymodule_app"))),

Templates

Each module needs two templates. The full page template extends global_base.html and is served on direct URL access. The partial template is standalone HTML loaded via AJAX when switching tabs (SPA behavior).

index.html — Full page: 

{% verbatim %}{% extends "global_base.html" %}
{% block content %}
    {% include "mymodule_app/index_partial.html" %}
{% endblock %}{% endverbatim %}

index_partial.html — AJAX partial: 

<div class="workspace-project-config" data-mode="mymodule">
    <!-- Your module content here -->
    <h2>My Module</h2>
    <p>Module content...</p>
</div>
The data-mode attribute must match your module's name in the registry. The tab switcher uses this for SPA navigation without page reloads.

Context Builder

The context builder function is called on both full page loads and AJAX partial loads. It must accept request and current_project: 

def build_mymodule_context(request, current_project=None):
    """Called by workspace shell for SPA tab switching."""
    return {
        "current_project": current_project,
        "my_data": MyModel.objects.filter(
            project=current_project
        ) if current_project else [],
    }

def index_view(request):
    """Full page view at /mymodule/."""
    project = get_current_project(request)
    context = build_mymodule_context(request, project)
    return render(request, "mymodule_app/index.html", context)

LLM Skill Registration

Register a Skill so AI assistants understand your module's capabilities. Create skill.py in your app: 

from apps.llm_app.skills import Skill, register
register(
    Skill(
        app_name="mymodule",
        display_name="My Module - Description",
        description="Detailed description for LLM context...",
        capabilities=[
            "Do something useful",
            "Process data",
        ],
        page_patterns=["/mymodule/"],
        url_prefix="/mymodule/",
        module_description="One-line summary.",
    )
)

CSS Variables & Theming

Use SciTeX CSS variables for consistent theming. Your CSS must be scoped under [data-mode="yourmodule"] to prevent style leaks: 

/* yourmodule_app/static/yourmodule_app/css/yourmodule.css */
[data-mode="yourmodule"] {
    --app-accent: var(--module-accent-yourmodule, #4a90d9);
}
[data-mode="yourmodule"] .my-card {
    background: var(--bg-primary);
    border: 1px solid var(--border-subtle);
    color: var(--text-primary);
}

Available theme variables:

Variable Description
--bg-primary Main background color
--bg-secondary Secondary/card background
--text-primary Main text color
--text-muted Subdued text color
--border-subtle Subtle border color
--accent Global accent color

Template Rules

User app templates are loaded from project directories with the following constraints:

  • Templates must not override protected blocks: extra_css, extra_js, content, title
  • Templates are standalone HTML fragments (AJAX partials), not full pages
  • The root element must have data-mode="yourmodule"
  • No {% verbatim %} {% extends %} {% endverbatim %} or {% verbatim %} {% load %} {% endverbatim %} tags allowed

TypeScript & Vite

Apps can include TypeScript files for interactive frontend logic. SciTeX uses a dual-Vite architecture to handle TypeScript compilation differently for platform modules and user-installed dev apps.

Vite Instance Port Scope Runs On
Host Vite 5173 Platform modules (Console, Writer, Scholar, etc.) Host machine (dev only)
Container Vite 5174 Developmentally-installed apps only Docker container (dev + prod)

Adding TypeScript to your app: 

your_app/
├── static/your_app/
│   ├── ts/
│   │   ├── main.ts              # Entry point (auto-discovered)
│   │   └── components/
│   │       └── widget.ts        # Additional modules
│   └── css/
│       └── your_app.css
└── templates/your_app/
    └── index_partial.html

TypeScript files under static/your_app/ts/ are auto-discovered by the container Vite server. No manual entry point configuration is needed.

Loading scripts in templates: 

{% verbatim %}{% load vite %}
{# In your template's script block #}
{% vite_script 'your_app/main' %}{% endverbatim %}
How it works: During developmental installation, the container Vite server (port 5174) serves your TypeScript files with Hot Module Replacement (HMR). Changes to .ts files are reflected in the browser without a full page reload. In production, the same Vite server runs behind an nginx proxy at /_vite_dev_app/.

App Lifecycle

Apps progress through distinct stages, each with different build behavior:

Stage TypeScript Build Visibility
1. Dev Install Live Vite dev server (port 5174) — HMR enabled, instant feedback Only the installing user
2. Validation scitex-cloud app validate . — checks structure —
3. Submit PR scitex-cloud app submit . — code review Reviewers
4. Published Pre-built bundle (Vite production build) — stable, versioned All users via Apps Catalog
Dev Install vs Published: During development, TypeScript is served live by the container Vite server for instant iteration. Once published, TypeScript is pre-built into static bundles — no live compilation needed, ensuring stability for all users.

Testing

ModuleTestMixin automatically validates all module layers. Create tests.py: 

from django.test import TestCase
from apps.workspace_app.test_mixin import ModuleTestMixin

class MyModuleTest(ModuleTestMixin, TestCase):
    module_name = "mymodule"

This validates:

Check What it verifies
test_module_registered Module exists in registry
test_partial_template_exists AJAX partial template file exists
test_icon_registered Has FontAwesome or SVG icon
test_context_builder_importable Context builder function is callable
test_ai_hint_defined LLM hint text is non-empty
test_accent_color_css_exists CSS variable --module-accent-{name} defined
test_skill_registered Skill exists in LLM registry

Submission Workflow

Apps follow a two-tier distribution model inspired by MELPA:

  1. Scaffold: scitex-cloud app init . — creates all boilerplate
  2. Develop: Edit templates, views, and CSS in your project
  3. Validate: scitex-cloud app validate . — checks structure and security
  4. Submit: scitex-cloud app submit . — opens a PR on the scitex/apps registry repository
  5. Review: Staff reviews the PR and merges to approve
  6. Live: Merged apps appear in the public Apps catalog for all users
Dev Install (no approval needed): Any user can dev-install your app directly from Hub Explore without going through the submission process. Dev installs are personal and only visible to the user who installed them.
Source code is automatically scanned for forbidden patterns (os.system, subprocess, eval, exec) before submission. The commit SHA is pinned on approval for reproducibility.

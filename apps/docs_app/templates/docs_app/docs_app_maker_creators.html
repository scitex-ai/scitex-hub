Your App Structure

When you create an app (via /new/ or the CLI), the scaffold generates this file structure. Here is what each file does: 

my_app/
├── templates/my_app/
│   ├── index.html              # Full page (direct URL access)
│   └── index_partial.html      # AJAX partial (tab switching)
├── static/my_app/css/
│   └── my_app.css              # Your app styles
├── docs/                       # Platform docs for AI agents
├── scitex/                     # SciTeX integration config
├── __init__.py
├── apps.py                     # Django app config (auto-generated)
├── views.py                    # Your page logic + data loading
├── urls.py                     # URL routing (auto-generated)
├── manifest.json               # App metadata, data schemas, jobs
├── skill.py                    # AI agent knowledge about your app
├── tests.py                    # Automated validation (auto-generated)
├── AGENTS.md                   # Instructions for AI coding tools
├── CLAUDE.md                   # Claude-specific project context
├── README.md                   # Project documentation
└── LICENSE                     # Your chosen license

Files You Edit

File What to do
templates/*/index_partial.html Build your UI here — this is the main content users see
views.py Load data for your templates, handle form submissions
static/*/css/*.css Style your app using SciTeX CSS variables
manifest.json Declare data schemas, jobs, and Platform Service dependencies
skill.py Describe your app so AI agents can assist users

Files You Can Ignore

apps.py, urls.py, tests.py, and __init__.py are auto-generated by the scaffold and work out of the box. The platform handles module registration, URL routing, and test validation automatically.

CLI Workflow (Recommended)

The fastest way to create and deploy a full app is via the scitex-cloud CLI. This gives you a complete project with manifest, Platform Services integration, and Gitea sync.

Step 1. Scaffold 

# Create a new app with all boilerplate
scitex-cloud app init /path/to/my_app --name my_research_app \
    --label "My Research Tool" --icon "fas fa-flask"

# Or with React frontend:
scitex-cloud app init . --name my_app --frontend react

Step 2. Develop locally 

# Initialize git
cd /path/to/my_app
git init && git add . && git commit -m "Initial scaffold"

# Edit manifest.yaml, views, templates, jobs...

Step 3. Upload to workspace 

# Creates project on server + Gitea repo + pushes code
scitex-cloud workspace upload --name my-research-app \
    --description "My research tool"

# Other workspace commands:
scitex-cloud workspace list          # List your projects
scitex-cloud workspace sync          # Pull + push changes
scitex-cloud workspace logout        # Clear cached token

Step 4. Validate and submit 

# Check app structure and security
scitex-cloud app validate .

# Submit for public listing (opens PR on scitex/apps registry)
scitex-cloud app submit . --token $SCITEX_CLOUD_TOKEN
The workspace upload command authenticates via JWT, creates a Django project (which auto-creates a Gitea repository), adds the git remote, and pushes your code.

Platform Services

Apps can use 7 built-in Platform Services via REST APIs instead of writing custom Django models, views, or Celery tasks. This lets you build powerful apps with just a manifest.yaml and frontend code.

Service API Prefix Purpose
DataStore /platform/api/data/ JSON-based CRUD with indexed virtual columns
FileVault /platform/api/files/ File upload/download scoped to app + project
JobQueue /platform/api/jobs/ Background task execution via Celery
ScitexBridge /platform/api/scitex/ Proxy to scitex Python package (io, stats, plt)
ExternalAPI /platform/api/external/ Proxied HTTP calls to whitelisted external services
RealtimeHub ws:// WebSocket channels for live updates
FrontendKit — Shared TS components (DataTable, Monaco, Viewer, Context Zoom)

Manifest

A manifest.yaml declares your app's data schemas, jobs, and service dependencies. Platform Services read this file to auto-configure everything. 

name: my-research-tool
label: My Research Tool
version: 0.1.0
icon: fas fa-flask
category: data
description: A tool for managing research samples.

datastore:
  Sample:
    fields:
      name: {type: string, max_length: 200, indexed: true}
      condition: {type: string, max_length: 100, indexed: true}
      measurement: {type: float}
      notes: {type: text}
      recorded_at: {type: datetime}
      tags: {type: json}
    permissions: owner_and_collaborators

jobs:
  export_samples:
    handler: my_research_app.jobs.export_samples.execute

scitex_modules: [io, stats]

The DataStore creates virtual indexed columns automatically — no Django migrations needed. Your frontend calls /platform/api/data/my-research-tool/Sample/ for CRUD operations.

No Django models required. The Platform Services DataStore provides JSON-based persistence with indexed lookups, so apps can store structured data without writing migrations.

Templates

Each app needs two templates. The full page template wraps your UI for direct URL access. The partial template is loaded via AJAX when switching tabs in the workspace.

index.html — Full page (from Pomodoro app): 

{% verbatim %}{% extends "global_base.html" %}
{% load static %}

{% block extra_css %}
    <link rel="stylesheet" href="{% static 'pomodoro_app/css/pomodoro_app.css' %}" />
{% endblock %}

{% block content %}
    {% include "pomodoro_app/index_partial.html" %}
{% endblock %}{% endverbatim %}

index_partial.html — AJAX partial (your main UI): 

<div data-pane-type="app"
     data-ai-hint="Pomodoro Timer App - focus timer with work/break intervals">
    <!-- Your app content here -->
    <h2>My App</h2>
    <p>Content...</p>
</div>
data-pane-type="app" marks this as an app pane. data-ai-hint gives AI assistants context about your app so they can help users more effectively.

Context Builder (views.py)

Your views.py provides data to your templates. Here is the real Pomodoro app's views.py — it is just 30 lines: 

from django.shortcuts import render
from apps.project_app.services.project_utils import get_current_project

def build_pomodoro_app_context(request, current_project=None):
    """Context builder — called for both full page and AJAX loads."""
    return {
        "current_project": current_project,
        "app_name": "Pomodoro",
        "app_description": "A simple Pomodoro timer.",
        "features": ["Work/Break intervals", "Session tracking"],
    }

def index_view(request):
    """Full page view for Pomodoro."""
    current_project = (
        get_current_project(request) if request.user.is_authenticated else None
    )
    context = build_pomodoro_app_context(request, current_project=current_project)
    return render(request, "pomodoro_app/index.html", context)
The context builder must accept request and current_project parameters. The workspace calls it for AJAX partial loading when users switch tabs. Return any data your template needs as a dictionary.

.pomodoro_app-container {
    background: var(--workspace-bg-tertiary);
    color: var(--workspace-text-primary);
    border: 1px solid var(--workspace-border-default);
}
.pomodoro_app-timer {
    background: var(--workspace-bg-secondary);
    color: var(--workspace-text-secondary);

Variable Description

--workspace-text-secondary Subdued text color
--workspace-bg-secondary Card/panel background

Template Rules

Your app has two template files with different rules:

File Rules
index.html Extends global_base.html, loads static files, includes your partial — follows standard Django template syntax
index_partial.html Standalone HTML fragment (no extends / load). Must have data-pane-type="app" on root element. Loaded via AJAX for tab switching.

TypeScript & Vite

Apps can include TypeScript files for interactive frontend logic. SciTeX uses a dual-Vite architecture to handle TypeScript compilation differently for platform modules and user-installed private apps.

Vite Instance Port Scope Runs On
Host Vite 5173 Platform modules (Console, Writer, Scholar, etc.) Host machine (dev only)
Container Vite 5174 Developmentally-installed apps only Docker container (dev + prod)

Adding TypeScript to your app: 

your_app/
├── static/your_app/
│   ├── ts/
│   │   ├── main.ts              # Entry point (auto-discovered)
│   │   └── components/
│   │       └── widget.ts        # Additional modules
│   └── css/
│       └── your_app.css
└── templates/your_app/
    └── index_partial.html

TypeScript files under static/your_app/ts/ are auto-discovered by the container Vite server. No manual entry point configuration is needed.

Loading scripts in templates: 

{% verbatim %}{% load vite %}
{# In your template's script block #}
{% vite_script 'your_app/main' %}{% endverbatim %}
How it works: During developmental installation, the container Vite server (port 5174) serves your TypeScript files with Hot Module Replacement (HMR). Changes to .ts files are reflected in the browser without a full page reload. In production, the same Vite server runs behind an nginx proxy at /_vite_dev_app/.

App Lifecycle

Apps progress through distinct stages, each with different build behavior:

Stage TypeScript Build Visibility
1. Private Install Live Vite dev server (port 5174) — HMR enabled, instant feedback Only the installing user
2. Validation scitex-cloud app validate . — checks structure —
3. Submit PR scitex-cloud app submit . — code review Reviewers
4. Published Pre-built bundle (Vite production build) — stable, versioned All users via Apps Catalog
Private Install vs Published: During development, TypeScript is served live by the container Vite server for instant iteration. Once published, TypeScript is pre-built into static bundles — no live compilation needed, ensuring stability for all users.

Testing

The scaffold generates a tests.py that automatically validates your app (registration, templates, icons, skills). You can add your own tests too. Here is the real Pomodoro app's test file: 

from django.test import TestCase
from apps.workspace_app.test_mixin import ModuleTestMixin

class PomodoroModuleTest(ModuleTestMixin, TestCase):
    """Auto-validates: registration, templates, icon, skill, CSS."""
    module_name = "pomodoro"

class PomodoroContextTest(TestCase):
    """Custom test for your context builder."""
    def test_context_has_required_keys(self):
        from django.test import RequestFactory
        from django.contrib.auth.models import User
        from apps.pomodoro_app.views import build_pomodoro_app_context

        request = RequestFactory().get("/pomodoro_app/")
        request.user = User(username="testuser")

        ctx = build_pomodoro_app_context(request)
        self.assertIn("app_name", ctx)
        self.assertEqual(ctx["app_name"], "Pomodoro")
ModuleTestMixin runs 7 checks automatically (registration, template, icon, context builder, AI hint, CSS, skill). You only need to set module_name — no test methods to write.

Submission Workflow

Apps follow a two-tier distribution model inspired by MELPA:

  1. Scaffold: scitex-cloud app init . — creates all boilerplate
  2. Develop: Edit templates, views, and CSS in your project
  3. Validate: scitex-cloud app validate . — checks structure and security
  4. Submit: scitex-cloud app submit . — opens a PR on the scitex/apps registry repository
  5. Review: Staff reviews the PR and merges to approve
  6. Live: Merged apps appear in the public Apps catalog for all users
Private Install (no approval needed): Any user can privately install your app directly from Hub Explore without going through the submission process. Private installs are personal and only visible to the user who installed them.
Source code is automatically scanned for forbidden patterns (os.system, subprocess, eval, exec) before submission. The commit SHA is pinned on approval for reproducibility.
